# 在 LX Agent 中复刻 Pi Agent 功能的设计方案

> 目标：在 `src/renderer/src/features/agent/AgentPage.tsx` 上复刻 pi（`/Users/yonah/projects/agent/pi-main`）编码 agent 的核心能力，复用 LX Agent 现有 harness（Electron 三进程 + `ai` SDK + MCP SDK + SQLite + 多 Provider 设置），仅输出本设计方案文档。
> 参考：pi-main `packages/agent`、`packages/ai`、`packages/coding-agent`、`packages/tui`。

---

## 1. 目标与边界

### 1.1 要复刻的（运行时能力对齐 pi）

- 真实多 Provider 流式对话（非当前 mock 打字机）。
- Agent 循环：消息 → LLM 流式回复 → 工具调用 → 工具结果回填 → 继续/结束。
- 工具系统：`read` / `grep` / `find` / `ls` / `edit` / `write` / `bash`。
- 会话持久化与历史：多会话、续聊、编辑/重发、会话标题。
- 上下文管理：system prompt 组装、项目上下文引用、上下文压缩（compaction）。
- 模型选择与切换、思考过程（thinking）展示、工具执行可视化。
- Slash 命令（桌面交互等价物）与基础配置。

### 1.2 不复刻的（形态差异，避免过度设计）

- 终端 TUI 及其组件库（`packages/tui`：editor-component、undo-stack、kill-ring、alt-screen 等）。
- `print-mode` / `json` 输出模式、`rpc-mode` + `packages/server` + `packages/client`（RPC 服务器）。
- CLI 参数系统（`cli/args.ts`）、会话树分支/fork/clone（桌面端仅做线性会话 + 删除）。
- 内置 40+ provider 的本地模型目录（复用 LX Agent 设置的 provider 配置即可）；远程模型目录刷新（remote-catalog-provider）按需再议。
- 扩展加载器（jiti 动态加载自定义工具/命令/slash）、`/export` HTML 导出、遥测/usage-totals 首版不做。

### 1.3 关键边界决策

- **运行时放 main 进程**：renderer 是沙箱（`BrowserWindow` 未开 nodeIntegration，`electron.vite.config.ts` 对 main/preload 用 `externalizeDepsPlugin`），`ai` SDK 与 MCP SDK 只能由 main 进程直接加载。流式结果经 IPC 事件推给 renderer。
- **不引入 pi 作为依赖**：优先用 LX Agent harness 原生实现。备选方案（以 RPC 子进程嵌入 pi）见 §7。
- **MCP 是增强项**：pi 本身无 MCP 支持，LX Agent 已装 `@modelcontextprotocol/sdk`，可让本方案的工具能力超出 pi，作为差异化。

## 3. 目标架构（复用 LX Agent 三进程 harness）

### 3.1 进程职责

```text
renderer（沙箱，只渲染）
  features/agent/        组件 + hooks + api（agent feature api 唯一入口）
      │  window.api.agent.*（preload 白名单）
preload
  api/agent.ts           薄转发：invoke 命令 + on(event) 订阅流式事件
      │  shared/ipc/agentChannels.ts（channel 常量，唯一来源）
main
  ipc/agentHandlers.ts   仅 handler 注册与参数边界
  agent/                 ★ agent 运行时（填充当前空目录）
    runtime/             agent loop（对应 pi agent-loop.ts）
    provider/            ai-sdk adapter（对应 pi stream-fn.ts / pi-ai）
    tools/               内置工具（read/grep/find/ls/edit/write/bash）+ MCP 客户端
    session/             会话服务（对应 pi session-manager.ts，改 SQLite）
    context/             system prompt + compaction（对应 pi system-prompt.ts / compaction/）
    events.ts            流式事件源（webContents.send）
  services/              agentService.ts（长生命周期：管理运行中会话、事件分发）
  db/schema/agentSchema.ts + migrations/  会话/消息/工具调用持久化
```

### 3.2 数据流

```text
发送消息：AgentInput ──sendMessage──▶ useAgentChat ──▶ agentApi.sendMessage(sessionId, text)
         ──IPC invoke──▶ ipc/agentHandlers ──▶ agentService.runTurn()
         ──▶ provider.streamText(...) + tools 循环
         ──▶ 事件源 webContents.send(AGENT_EVENT, evt)
         ──▶ preload.on(evt) ──▶ useAgentChat 追加消息/工具块 ──▶ 渲染
停止：    stop() ──▶ agentService.abort() ──▶ 底层 AbortController 终止流
```

## 5. 数据契约与 IPC 设计

### 5.1 `src/shared/agent.ts`

```ts
// 消息角色（工具调用不单独成行，挂在 assistant 的 toolCalls）。
export type AgentMessageRole = "user" | "assistant"

// 工具调用。
export type AgentToolCall = {
  id: string
  name: string
  input: Record<string, unknown>
  output?: string          // 结果文本
  status: "pending" | "running" | "success" | "error"
  startedAt?: number
  finishedAt?: number
}

// 消息。
export type AgentMessage = {
  id: string
  sessionId: string
  role: AgentMessageRole
  content: string           // markdown / 工具结果文本
  thinking?: string
  toolCalls?: AgentToolCall[]
  createdAt: number
}

// 会话（一个 project item 可对应多个会话）。
export type AgentSession = {
  id: string
  projectItemId: string
  title: string
  model: { provider: string; model: string }
  createdAt: number
  updatedAt: number
}

// 流式事件（preload.on 订阅，webContents.send 推送）。
export type AgentEvent =
  | { type: "turn_start"; sessionId: string }
  | { type: "text_delta"; sessionId: string; messageId: string; delta: string }
  | { type: "thinking_delta"; sessionId: string; messageId: string; delta: string }
  | { type: "tool_call_start"; sessionId: string; call: AgentToolCall }
  | { type: "tool_call_output"; sessionId: string; call: AgentToolCall }
  | { type: "message_complete"; sessionId: string; message: AgentMessage }
  | { type: "turn_end"; sessionId: string }
  | { type: "error"; sessionId: string; message: string }
```

### 5.4 数据表设计（对齐现有 `projectSchema` 规则）

设计依据当前 `src/main/db/schema/projectSchema.ts` 与 `projectService.ts` 的既有规则：主键 `id INTEGER PRIMARY KEY`；业务主键 `external_id TEXT NOT NULL UNIQUE`（`randomUUID()`）；外键引用父表 `external_id` 且 `ON DELETE CASCADE`；时间戳 `TIMESTAMP NOT NULL`（ISO 字符串）；枚举用 `CHECK`；扩展数据用 JSON 列（`TEXT NOT NULL DEFAULT '[]'`）；索引 `idx_表_列`；`connection.ts` 已开 `foreign_keys = ON`。

#### agent_session（会话）

| 列 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PRIMARY KEY | 自增内部主键 |
| external_id | TEXT NOT NULL UNIQUE | 业务主键，`randomUUID()` |
| project_item_id | TEXT NOT NULL | 归属的 project item，外键 → `project_item(external_id)`，`ON DELETE CASCADE`；一个 item 可对应多个会话 |
| title | TEXT NOT NULL DEFAULT '' | 会话标题（P2 由 titleSummary 模型生成） |
| provider | TEXT NOT NULL | 会话所用模型 provider id（对齐 `ModelSelection`） |
| model | TEXT NOT NULL | 会话所用模型 id |
| created_at | TIMESTAMP NOT NULL | ISO 字符串 |
| updated_at | TIMESTAMP NOT NULL | 每次 turn 结束刷新，历史列表按此倒序 |

```sql
CREATE TABLE IF NOT EXISTS agent_session (
  id INTEGER PRIMARY KEY,
  external_id TEXT NOT NULL UNIQUE,
  project_item_id TEXT NOT NULL,
  title TEXT NOT NULL DEFAULT '',
  provider TEXT NOT NULL,
  model TEXT NOT NULL,
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL,
  FOREIGN KEY (project_item_id) REFERENCES project_item(external_id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_agent_session_project_item_id ON agent_session(project_item_id);
```

#### agent_message（消息）

| 列 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PRIMARY KEY | 自增内部主键 |
| external_id | TEXT NOT NULL UNIQUE | 业务主键，`randomUUID()` |
| session_id | TEXT NOT NULL | 外键 → `agent_session(external_id)`，`ON DELETE CASCADE` |
| role | TEXT NOT NULL CHECK (role IN ('user','assistant')) | 只落库 user / assistant 两角色 |
| content | TEXT NOT NULL DEFAULT '' | 用户输入 / assistant 最终 markdown |
| thinking | TEXT | assistant 思考过程，可空 |
| tool_calls | TEXT NOT NULL DEFAULT '[]' | JSON：`AgentToolCall[]`（含结果 output） |
| created_at | TIMESTAMP NOT NULL | ISO 字符串 |
| updated_at | TIMESTAMP NOT NULL | 编辑/重发时刷新 |

```sql
CREATE TABLE IF NOT EXISTS agent_message (
  id INTEGER PRIMARY KEY,
  external_id TEXT NOT NULL UNIQUE,
  session_id TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
  content TEXT NOT NULL DEFAULT '',
  thinking TEXT,
  tool_calls TEXT NOT NULL DEFAULT '[]',
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL,
  FOREIGN KEY (session_id) REFERENCES agent_session(external_id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_agent_message_session_id ON agent_message(session_id);
```

#### 设计要点

- **会话归属 project item**：`agent_session.project_item_id` 引用 `project_item(external_id)`，一个 item 多个会话；删除 item 级联删除其全部会话与消息。侧栏会话列表按当前选中 item 过滤。
- **工具调用不建独立表**：一次 assistant 消息的"思考 + N 个工具调用（含结果）+ 最终文本"是完整单元，且一次会话工具调用不过几十个，JSON 列足够（与 `project.referenced_folders` 的 JSON 列先例一致）。会话加载按 `ORDER BY created_at ASC, id ASC` 读回后，再从 `tool_calls` 展开成喂回 LLM 的 user/assistant/toolResult 序列。
- **不用 `sort_order`**：消息是自然追加顺序，现有查询风格 `created_at ASC, id ASC` 即可（`project_item.sort_order` 因用户手动排序才需要）。
- **会话模型存 provider+model 快照**：切换模型不影响历史会话恢复。
- 查询示例：历史列表 `SELECT * FROM agent_session WHERE project_item_id = ? ORDER BY updated_at DESC, id DESC`；加载会话 `SELECT * FROM agent_message WHERE session_id = ? ORDER BY created_at ASC, id ASC`。

#### 落点与迁移

- 新建 `src/main/db/schema/agentSchema.ts` 导出 `createAgentTables(database)`，仿照 `createProjectTables`，并在 `connection.ts` 的 `initDatabase()` 中于 `createProjectTables` 之后调用。
- 项目规范要求"schema 变更必须新增独立迁移文件，不能修改既有迁移以伪造历史"，但当前仓库尚无 `migrations/` 目录与迁移执行机制。落地建议：agent 表属新增，`CREATE TABLE IF NOT EXISTS` 幂等追加即可，先不伪造历史；引入正式迁移机制（`migrations/` + `schema_migrations` 表）列为独立技术债。

## 7. 风险与决策点

| # | 决策点 | 选项 | 建议 |
|---|---|---|---|
| 1 | **"一模一样"的边界** | 全量复刻 vs 运行时对齐 | 按 §1.2 边界：形态可裁剪，运行时能力对齐 pi；范围以本表 P0-P2 为验收 |
| 2 | **原生移植 vs RPC 嵌入 pi** | ① 用 harness 原生实现（本方案）；② 把 pi 当子进程，经 `rpc-mode`/`packages/server` 交互 | 推荐 ①：无新增外部依赖、复用 LX 设置与 MCP、符合最小修改。② 仅在要 100% 复刻 pi 语义且不想维护移植时考虑，代价是引入整个 monorepo |
| 3 | **工具安全边界** | bash/edit/write 是否首版开放 | 首版只读工具 + MCP；写/执行工具进 P2 并做权限确认，避免桌面侧栏误操作风险 |
| 4 | **会话存储格式** | SQLite vs JSONL | 用 SQLite（复用 harness、可查询、与现有项目表一致）；不引入 pi 的 JSONL 格式 |
| 5 | **apiKey 存储** | 明文配置文件（沿用现状） vs keychain/OAuth | 首版沿用明文，与 settings 现状一致；keychain 列为后续 |
| 6 | **流式推送通道** | `webContents.send` 事件 vs `ipcRenderer.invoke` 长轮询 | 用事件推送（单窗口场景最简单）；多窗口/后续扩展再抽象 |
| 7 | **380px 侧栏承载度** | 侧栏聊天 + 工具面板 vs 独立 Agent 页面 | 工具块/thinking 折叠可放侧栏；bash 长输出建议"点击展开新面板"避免挤压 |
| 8 | **MCP 是否纳入** | 是（超越 pi） vs 否 | 建议纳入，`@modelcontextprotocol/sdk` 已装，是 LX Agent 差异化能力 |

## 9. 结论

LX Agent 的 harness（`ai` SDK、MCP SDK、多 Provider 设置、SQLite、LxMarkdown、项目引用）与 pi 的能力面高度互补：harness 提供了 pi 需要自研的 provider 层、MCP 与 UI 底座，缺的是 agent 运行时本身。因此**核心工作量集中在 `src/main/agent/`（运行时、工具、会话、上下文）与一套 `shared` 契约 + IPC**，renderer 侧仅需在现有 `AgentPage` 上扩展工具块、thinking 与选择器。按 P0 → P1 → P2 落地，即可在桌面侧栏中达到"与 pi 一致"的 agent 体验，并在工具（MCP）上形成超越。

> 调研方法：结合 codebase-memory MCP（`pi-main` / `lx-agent` 两个知识图谱）定位 pi 各能力域的关键实现文件，配 codegraph 交叉验证调用关系，再按本仓库 `docs/` 规范与三进程依赖方向设计落点。
